# 宿舍上床下桌取件辅助机械臂

> **摘要：面向宿舍"上床下桌"场景，实现了语音点名-视觉识别定位-平衡约束下搬运的完整取件流程。
> 因为软件尚未定型，本阶段以合成视觉 + 物理仿真**替代实体硬件，
> 构建了一套**零硬件依赖、可复现、可量化**的算法验证平台。

**现实需求**：宿舍床上想喝水、拿手机、拿书，必须下床爬梯子，再拿东西上床。现在有了桌面机械臂，一切取物步骤直接简化为对机械臂说一句话。
**市场现有产品在该环境下的不足**：（如 myCobot 280）臂展不够，覆盖不了 900 mm 的垂直行程，也没有针对"搬运开口容器"的平衡设计。

## 3. 关键技术说明

### 3.1 视觉识别与伺服定位

**识别：四级过滤，逐级淘汰**

| 级别  | 方式                                                                                               | 消除的问题                                        |
| --- | ------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| 1   | 参考图自动抠背景生成掩膜，只对物品区域提特征点                                                                          | 背景相似导致的错误匹配                                  |
| 2   | 检测是否"一枝独秀"：将登记物匹配程度最高的两组特征点进行对比，若第一名的相似程度高于第二名相似程度的25%，则说明第一组够准确；未超过，则说明两组均不准确，丢弃该次数据，采用新一组角度的数据 | 一级过滤时，背景扣除不完全带来的风险；选取到两组均不准确的特征点；对物品重复纹理的误匹配 |
| 3   | 几何一致性检验：用 RANSAC 求一个统一的单应矩阵，统计有多少组匹配能被同一变换一致解释（内点）；并检查投影框的面积与长宽比是否合理                             | "物品摆放角度与登记时不同"造成的透视变形                        |
| 4   | 把框内画面与参考图物品区域做 HSV 直方图（色相+饱和度）相关性比较                                                              | 几何相似但颜色分布不同的物品间的误判（实测同物 0.95 / 异物 0.10）      |

得分 `score = 0.50×内点比例 + 0.30×内点数量(按参考图关键点数归一化) + 0.20×直方图相关`。

**定位方式**：用单应矩阵求尺度、用内点质心定位置 —— 这样从物体任何部位匹配上都能定位到中心
（早期版本只用投影框，当匹配点集中在杯子条纹上时框会偏大且偏移）。

**像素→角度用针孔反投影** `Δθ = atan(Δpx / f)`，与渲染器、伺服闭环统一同一个几何模型。

**验证结果**（`python run.py verify --frames` 全自动跑完并导出过程拼图到 `out/`）：

| 验证项     | 实测结果                                                  |
| ------- | ----------------------------------------------------- |
| 定点识别误差  | **0.00° / 0.04° / 0.00°**（三件物品），得分 0.97 / 0.89 / 0.96 |
| 误检抑制    | 6 次识别位置偏差 **0 像素**，误检 **0 次**（未登记物品被正确忽略）             |
| 视觉伺服闭环  | 14 / 11 / 22 步收敛，误差 **1.34° / 0.10° / 0.15°**         |
| 全行程扫描定位 | 误差 **0.19° / 0.19° / 0.00°**                          |

### 3.2 平衡控制：把水看成单摆

```
等效摆长    L = R / (1.841 · tanh(1.841 · h / R))，不小于 R
固有频率    f₁ = (1/2π)·√(g/L)
惯性系动力学 θ_abs'' = −(g/L)·sin θ_abs + (a_cup/L)·cos θ_abs − c·θ_abs'
杯子惯性倾角 θ_cup = −a_cup / g
相对杯口倾角 θ_liquid = θ_abs − θ_cup
```

**核心认识：液面总倾角是两部分叠加的**

| 成分                  | 由什么决定             | 治理手段          |
| ------------------- | ----------------- | ------------- |
| 准静态倾斜 ≈ arctan(a/g) | 加速度**幅值**         | 压低加速度（离线优化查表） |
| 振荡（频率固定在 f₁）        | 加速度**突变程度**（jerk） | 输入整形（ZVD）     |

实测两者量级相当（缓慢斜坡工况下振荡分量 4.65° > 准静态 1.53°），**必须分开治、不能互相替代**。

**ZVD 输入整形**：把加速度指令与三个脉冲做卷积，脉冲间隔为半个晃动周期（375/2 ≈ 188 ms），
让晃动相位相反、自相抵消。整形前后**指令面积守恒 99.5% 以上**（面积不守恒 = 峰值被假性削弱，结果不可信）。

**离线优化 + 查找表**：实时抑制晃动很难（没有便宜的液面传感器，视觉测液面延迟大、噪声大，
闭环相位错了反而放大晃动）；而宿舍场景物品种类与搬运距离有限，**穷举成本极低**。
所以离线二分搜索出"不超倾角的最大加速度"做成表，运行时只剩查表 + 限幅。

**验证结果**（`python -m vision_arm.balance`，会重跑对照实验、重算查找表并写入 `out/balance_plan.json`）：

同一杯水（半径 35 mm、液深 60 mm → 晃动频率 **2.66 Hz**、周期 **375 ms**），转角 90°：

| 方案                      | 液面峰值倾角     | 用时     | 实际峰值加速度    | 结论       |
| ----------------------- | ---------- | ------ | ---------- | -------- |
| ① 粗暴搬运（方波 120°/s²）      | **23.70°** | 1.78 s | 120.0 °/s² | ❌ 严重洒出   |
| ② 只做 S 曲线（仍想快）          | 6.11°      | 6.05 s | 60.0 °/s²  | ❌ 仍超标    |
| ③ 只做输入整形（方波+ZVD）        | 15.03°     | 1.78 s | 120.0 °/s² | ❌ 光整形救不回 |
| ④ **本方案：离线优化+S曲线+输入整形** | **3.00°**  | 4.38 s | 28.9 °/s²  | ✅ 合格     |

> **结论**：液面峰值倾角从 23.70° 压到 3.00°（**降低 87%**），代价是搬运时间 1.78 s → 4.38 s。
> 
> ② 与 ③ 的对比特别说明问题：只做输入整形（③）把方波从 23.70° 降到 15.03°（降 37%），
> 说明**整形确实有效**；但加速度仍是 120°/s²，所以照样洒。**整形治的是"晃"，治不了"倾"。**

**离线查找表**（安全峰值加速度，°/s²）：

| 等级               | 10°  | 20°   | 40°   | 60°   | 90°   | 120°  |
| ---------------- | ---- | ----- | ----- | ----- | ----- | ----- |
| **A** 开口液体（≤3°）  | 20.0 | 28.3  | 28.9  | 28.9  | 28.9  | 28.9  |
| **B** 易损瓶装（≤8°）  | 40.0 | 56.6  | 75.1  | 76.7  | 76.3  | 76.3  |
| **C** 普通物品（≤20°） | 77.5 | 109.5 | 154.9 | 189.7 | 185.6 | 185.6 |

A 级在 20° 后卡在 28.9 不动，说明限制因素从"距离不够"变成了"倾角超限"。
同一条轨迹：C 级能跑 185 °/s²（1.8 秒），A 级只敢跑 28.9 °/s²（4.4 秒）——**慢下来的是在给"不洒水"买单**。

### 3.3 行人避让：分层安全域

| 距离          | 动作              |
| ----------- | --------------- |
| > 0.8 m     | 正常搬运            |
| 0.5 ~ 0.8 m | 速度降至 30%        |
| 0.3 ~ 0.5 m | 停止前进，**原地保持姿态** |
| < 0.3 m     | 缓速远离            |

**关键设计：不是急停，而是逐级减慢。** 急停本身就是一个巨大的减速度，水会直接晃出来。

三重冗余：视觉检测行人 + 电机电流突变检测碰撞 + 硬件急停与下位机看门狗。

## 4. 开发过程中发现并解决的问题（21 项）

> 这一节是这个项目最有价值的部分：**下面每一条都是"代码写完、跑起来之后"才暴露的**，静态检查一个都发现不了。

**举三个最有代表性的：**

**1.  合成相机其实只有约 1° 视场（识别层）**

仿真器里用的相机模型与算法不同，仿真中用的是针孔相机，其计算视场的公式与算法中用焦距反推视场的公式不同，导致实际应为53°视场的相机在仿真器中变为了1°，进而导致模拟场景中的识别效率很低。这很容易误认为是算法太低效了，但其实不是。我改了半天算法才发现是仿真出问题了。

**2.  用不确定的哈希值播种产生随机纹理检测样照，导致除第一次外识别效果大幅降低（识别层）**
为了简化现实模型，先前我采用了hash来播种生成随机纹理的低分辨率物品图，供算法检验，导致用于识别的参考图未变（读取于本地磁盘），而检验时的渲染画面（每次随机生成）却产生了极大不同，导致渲染效果变差，识别准确率在 0.49~0.93 之间跳，具体表现就是：同一个样本与数据，在家里与学校的两台电脑跑了两次，结果都不同。我通过换掉哈希函数，改用zlib.crc32，解决了此问题。

**3.  单摆模型忽略了在惯性作用下液面与杯子间产生的相对角度（平衡层，最有价值的一条）**
模型把液面简化为单摆，这对于水杯与水的部分运动过程中是成立的，即当水在机械臂运动中期，速度与水杯一致时，水与杯子的相对角度为零，此时的水与杯子可视为一个单摆。但是在运动的初期与末尾，加速度变化最大的时候，水的液面因为惯性，会先在短暂时间保持水平，与水杯产生相对角度，这时候的液面的位置带来的影响是不可忽略的，若像初版一样，直接带入单摆模型的数据来做液面平衡，会导致低估倾角，使安全性不足。考虑惯性后问题就解决了。

## 5. 接真实硬件

硬件最小集：1 轴转台（步进电机 + STEP/DIR 驱动器 + 减速）、相机固定在转台上与夹爪同轴、
Arduino 烧 `firmware/arduino_motor_servo.ino`、急停按钮、垂直轴用**自锁丝杆**。

协议是 ASCII 行协议（见 `vision_arm/motor.py` 顶部）：

```
MOVE A 12.500 F 30.00     ->  OK MOVE A 12.500
STATUS A                  ->  POS A 12.480 MOVING 0
STOP A                    ->  OK STOP A
```

固件做了三重保护：**800 ms 收不到指令自动停并抱闸**、软限位、急停锁存。上位机崩了不会飞车。

先空跑确认协议，再上电：

```bash
python run.py move 水杯 --port COM5 --dry-run   # 只发指令不驱动
python run.py move 水杯 --port COM5             # 真正驱动
```

**换真实相机只需实现一个类**，`Servo` 和 `Detector` 一行都不用改（实现 `grab(dt)` 返回 BGR 帧、
`sync(deg)` 记录当前电机角度、`cam_deg` 属性）。要点：**`cam_deg` 必须是"这一帧曝光时刻的实际电机角度"**，
用指令角度代替会因机械回差引入 1~3° 系统误差。

## 6. 常见问题

| 现象                                     | 原因与处理                                                         |
| -------------------------------------- | ------------------------------------------------------------- |
| 报错没有 SIFT                              | 装了 `opencv-python`，换成 `opencv-contrib-python`                 |
| `python` 命令不可用                         | 装 Python 时没勾 "Add python.exe to PATH"，用完整路径调用                 |
| `pip install -r requirements.txt` 编码报错 | 依赖文件里有非 ASCII 字符；直接 `pip install opencv-contrib-python numpy` |
| `cv2.imread` 打不开中文路径                   | OpenCV 在 Windows 上用 ANSI 打开文件；本项目用 `imgio.py` 绕开了这个坑          |
| 参考图自检不过                                | 图太糊/纯色/关键点太少。换纹理更丰富的图，或把物品贴近拍大一点                              |
| 台账里认不出物品                               | 现场光照与登记时差太多。用现场光重拍参考图；或调低 `min_score` 到 0.45                  |
| 越转越偏                                   | `move_sign` 反了，跑 `calibrate` 或手动改 `-1`                        |
| 到了目标附近来回抖                              | 调小 `gain`、减小 `max_step_deg`、加大 `settle_s`                     |

## 7. 已知局限与下一步

**如实说明的局限**：

1. 视觉验证是在**合成场景**里做的，实机上还有光照与标定问题要解决；
2. 行人检测目前用**仿真数据**，还没有接真实传感器；
3. 机械结构仍在设计阶段（成本估算 3000~5000 元）。

**下一步**：

| 阶段  | 内容                               | 关键改动                                |
| --- | -------------------------------- | ----------------------------------- |
| 1   | 单轴转台 + 真相机，跑通"看→转"               | 新增 `RealCamera` 类（约 30 行）           |

| 5   | 优化斜坡策略（让加速段持续整数个晃动周期），看能否提高安全加速度 | 当前 28.9 °/s² 已接近纯准静态极限              |
